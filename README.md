## Сценарий

Путь от создания типа встречи до появления записи у владельца.

Владелец:

1. Открывает список типов встреч и создаёт новый: название, описание, длительность (например, «Консультация», 30 минут).
2. Новый тип сразу доступен гостям по своей ссылке. Свободное время считается по рабочим часам владельца в его часовом поясе.

Гость:

3. Без регистрации открывает страницу владельца и выбирает тип встречи.
4. Видит календарь с ближайшими днями и выбирает дату. Справа появляются свободные слоты, длина слота равна длительности типа встречи.
5. Выбирает слот. Время, уже занятое любой встречей, в списке не показывается.
6. Вводит имя и email и подтверждает запись.
7. Видит страницу подтверждения: что, когда, с кем.

Владелец:

8. Открывает список предстоящих встреч и видит новую запись (тип, дата, время, гость) среди встреч всех типов.
9. Этот слот пропадает из свободных у всех типов встреч, в том числе у других типов с пересекающимся временем.

## Обязательные функции

- Владелец один и задан заранее.
- Владелец создаёт типы встреч: название, описание, длительность.
- Владелец видит список предстоящих встреч всех типов.
- Гость без регистрации выбирает тип встречи и видит календарь на 14 дней вперёд.
- Гость бронирует свободный слот, длительность слота равна длительности типа встречи.

## Ограничения

- Нет авторизации, личных кабинетов, интеграций с внешними календарями и уведомлений.
- Окно записи 14 календарных дней, сдвигается со временем.
- Одно время нельзя занять дважды, даже разными типами встреч, включая частичное пересечение. Встреча может начинаться в момент окончания предыдущей.
- Правило о пересечениях действует и для одновременных запросов.
- Приложение собирается в Docker-образ и запускается в контейнере.
- Типы встреч, записи и результаты попыток сохраняются в SQLite.

## Требования к API

- Контракт описывается на TypeSpec.
- Из контракта генерируется OpenAPI-спецификация.
- Клиентский SDK для фронтенда генерируется из OpenAPI. Генератор должен существовать для языка фронтенда.
- Серверные типы и маршруты генерируются, если фреймворк это поддерживает. Иначе бекенд реализуется по контракту и проверяется тестами.

## Установка

Установите [mise](https://mise.jdx.dev/getting-started.html). Версии Node.js, pnpm, hk и pitchfork зафиксированы в `mise.toml`. На Intel macOS для сборки hk и pitchfork дополнительно нужны Rust и Cargo.

```bash
git clone https://github.com/AndreyPlotnikov/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install
mise run setup
```

`setup` устанавливает зависимости по lockfile и Git-хук pre-commit. Для установки только зависимостей используйте `mise run install`. Запускайте команды через `mise exec --`, если mise не активирован в оболочке.

## OpenCode в GitHub

Workflow [opencode.yml](.github/workflows/opencode.yml) вызывает официальную GitHub-интеграцию OpenCode CLI V1 (`opencode github run`) из комментариев к issues, PR и строкам diff. Используется провайдер OpenCode Zen, а не подписка локальной сессии.

Перед первым запуском:

1. Установите [GitHub App opencode-agent](https://github.com/apps/opencode-agent/installations/new), выбрав **Only select repositories → ai-for-developers-project-387**. Проверьте запрашиваемые разрешения и подтвердите установку.
2. В [консоли OpenCode](https://opencode.ai/console) создайте API-ключ. В [Actions secrets](https://github.com/AndreyPlotnikov/ai-for-developers-project-387/settings/secrets/actions) добавьте repository secret `OPENCODE_API_KEY`. Не публикуйте ключ в комментариях или Git. Для платных моделей нужны средства на балансе; настройте бюджет в консоли.
3. Выберите доступную вашему аккаунту модель Zen (`opencode models opencode` в CLI V1) и сохраните её полный ID `opencode/<model-id>` в repository variable `OPENCODE_MODEL` в [Actions variables](https://github.com/AndreyPlotnikov/ai-for-developers-project-387/settings/variables/actions).
4. Доставьте workflow в ветку `main`: событие `issue_comment` использует workflow из основной ветки. До этого вызовы из комментариев не работают.

Для проверки оставьте отдельный комментарий в issue:

```text
/oc Объясни эту задачу и предложи план. Не изменяй файлы.
```

Команда `/oc` или `/opencode` должна начинать строку (регистр неважен). Вызов разрешён только людям с текущими правами `write`, `maintain` или `admin`; боты и пользователи без этих прав не получают доступ к секрету и OIDC. Проверьте запуск **OpenCode** во вкладке Actions и ответ приложения в обсуждении.

В issue агент может создать ветку и PR; в PR — отправить изменения в его ветку. Перед вызовом на PR проверьте код, особенно из форка: агент выполняет команды с доступом к API-ключу и токену приложения. Проверка прав автора комментария не защищает от вредоносного содержимого задачи или PR. Начальный checkout берётся из основной ветки, но агент может переключиться на ветку PR.

`GITHUB_TOKEN` имеет `contents: read` и `actions: read` для счётчика; право `id-token: write` нужно для обмена OIDC на токен GitHub App, которым агент отвечает и отправляет изменения. Публичный шаринг сессий отключён, вызов агента ограничен 35 минутами, задание — 45 минутами. Перед изменениями агент читает `AGENTS.md`, включая требование `mise run check`; инструменты и зависимости проекта устанавливаются workflow.

### Независимое ревью PR и бюджет обращений

[OpenCode independent review](.github/workflows/opencode-review.yml) запускается отдельно на открытии, повторном открытии, изменении и готовности PR к ревью. Допущены PR владельца и приложения `opencode-agent` из этого репозитория в основную ветку; форки не получают ключ. В настройках приложения проверьте фактический login автора PR. Для ревью используется обычный CLI с теми же `OPENCODE_API_KEY` и `OPENCODE_MODEL`: он получает [критерии календаря](REVIEW.md), diff, описание, обсуждение, ссылки на связанные issues и результаты CI. Ревьюер не исправляет код; комментарий публикуется отдельным шагом. Тайм-аут — 20 минут, новый запуск отменяет прежний для того же PR. Приложение по-прежнему требует решения человека: проверяйте наличие согласования, статусы и SHA перед мержем. PR из `GITHUB_TOKEN` может ожидать ручного разрешения запуска Actions.

В [шаблоне PR](.github/pull_request_template.md) укажите ссылки на исходное обращение, спецификацию, согласование и задачи, а также проверки с SHA, риски и откат. Для спецификации редактирования типа встречи это #2, #3 и #4–#7. Проверка работающей версии из точного head SHA и демонстрация отсутствия/поломки поведения относятся к следующему этапу реализации.

Интерактивный OpenCode ограничен тремя кандидатами на запуск на один PR. Источник счётчика — история Actions этого workflow: учитывается `run_attempt`, включая повторные и отменённые попытки. Оба типа комментариев попадают в один счётчик. Проверка находится внутри вызываемого задания, чтобы повтор отдельного задания не обошёл её. Для безопасности учитываются и неподходящие комментарии, содержащие `/oc` или `/opencode`, даже если автор не прошёл проверку прав или команда не была допущена: они могут исчерпать бюджет преждевременно. При отсутствии данных истории запуск блокируется. Не удаляйте историю запусков: её удаление может занизить счётчик. У GitHub App агента должно быть не более `actions: read`, иначе агент сможет изменить историю. Новый PR получает новый бюджет; администратор может изменить конфигурацию или историю.

При исчерпании отдельное задание сообщает `limit_exhausted`, текущий SHA и ссылку на логи; человек выбирает дальнейшие действия. При сбоях подготовки или агента также публикуется причина. Полная отмена workflow и недоступность GitHub API могут помешать публикации отчёта; в таком случае смотрите логи Actions. Перед использованием проверьте на тестовом PR общий и построчный комментарии, параллельные, отменённые и повторные запуски, четвёртый отказ без вызова модели и корректную классификацию тайм-аута. Настройка обязательного CI на основной ветке выполняется в настройках GitHub отдельно; если тариф её не поддерживает, перед мержем человек вручную сверяет результаты и SHA.

### Автотриаж новых обращений

Workflow [opencode-triage.yml](.github/workflows/opencode-triage.yml) запускается при открытии issue после доставки workflow в `main`. Он использует те же `OPENCODE_API_KEY`, `OPENCODE_MODEL` и GitHub App. Агент изучает обращение и приложение, оставляет предварительный разбор и вопросы; согласование поведения остаётся за человеком. Для продолжения обсуждения используйте `/oc`.

Запуск разрешён только issue от людей с текущими правами `write`, `maintain` или `admin`. Issue с меткой `ready-for-agent` пропускаются: спецификации и тикеты, подготовленные скиллами, не нуждаются в повторном триаже. Метка должна быть установлена при создании issue; workflow повторно проверяет её перед запуском агента. Для ограничения расходов используется одна общая группа параллелизма: GitHub Actions выполняет один запуск и оставляет не более одного ожидающего, заменяя предыдущий ожидающий новым. Тайм-аут проверки прав — 5 минут, триажа — 15 минут.

Проверка после доставки в `main`: откройте новое обращение от доверенного автора без `ready-for-agent` и проверьте запуск **OpenCode issue triage** и комментарий. Отдельно создайте подготовленное тестовое issue с меткой `ready-for-agent` при создании и убедитесь, что задание пропущено. Не добавляйте метку после открытия в расчёте на гарантированный пропуск: запуск может начаться раньше.

## Проверки

```bash
mise run check
```

Команда запускает линтеры, проверку форматирования и типов, тесты бекенда, сборку фронтенда и браузерные E2E-тесты Playwright. Playwright устанавливает Chromium Headless Shell при первом запуске и переиспользует его при следующих. Ту же команду запускают `pre-push` и GitHub Actions.

### Quality gates

`mise run check` включает проверку зависимостей через OSV (требуется сеть), поиск секретов, неиспользуемого кода и циклических импортов, проверку схем и воспроизводимости генерации. Git-хук `pre-commit` проверяет изменённые файлы, `commit-msg` — Conventional Commits, а `pre-push` запускает полный набор. После изменения конфигурации хуков выполните `mise run setup`.

GitHub Actions запускает проверки при каждом push, pull request и раз в неделю. Конфигурация `renovate.json` подготовлена для Renovate; чтобы бот создавал pull request, его приложение должно быть подключено к репозиторию.

Knip исключает сгенерированные файлы: генераторы намеренно создают экспорты с запасом. В backend из проверки неиспользуемых зависимостей также исключены пакеты, импортируемые TypeSpec, и инструменты, вызываемые из корневых задач и Git-хуков.


Фоновые серверы можно запустить и остановить через mise:

```bash
mise daemons start
mise daemons status
mise daemons logs
mise daemons stop
```

## Запуск в Docker

Соберите образ из корня проекта и запустите контейнер с именованным томом.

```bash
docker build -t call-calendar .
docker run -d --name call-calendar -p 127.0.0.1:3000:3000 \
  --mount type=volume,source=call-calendar-data,target=/data call-calendar
```

Интерфейс открыт по адресу `http://localhost:3000`, API доступен на том же порту. Если порт занят, измените первый номер порта после `127.0.0.1:` и откройте соответствующий адрес.

В контейнере файл `/data/call-calendar.sqlite` хранит типы встреч, записи и результаты попыток создания и записи. Чтобы проверить сохранность при замене контейнера, выполните `docker stop call-calendar` и `docker rm call-calendar`, затем повторите команду запуска с тем же томом. Откройте созданный ранее тип по его прямой ссылке и проверьте список предстоящих встреч.

## Публичный деплой

Приложение первого проекта было развёрнуто на Render: https://call-calendar-f3yf.onrender.com (проверка: https://call-calendar-f3yf.onrender.com/health). Этот сервис относится к первому репозиторию; развёртывание текущего проекта отдельно не настроено.

Сервис `call-calendar` создан как web service с Docker runtime из `Dockerfile` в корне, ветка `main`, бесплатный тариф, регион Frankfurt. Render задаёт `PORT`, `HOST=0.0.0.0` уже в образе. Автодеплой по push не работает: на репозиторий не установлено GitHub-приложение Render, поэтому деплой запускается вручную (кнопка Manual Deploy в Render Dashboard или `trigger_deploy` через Render MCP). Новый деплой сбрасывает SQLite.

**Ограничение хранения данных.** К сервису не подключён постоянный диск (на бесплатном тарифе его нет), поэтому `/data/call-calendar.sqlite` лежит на эфемерной файловой системе контейнера. При перезапуске, засыпании после простоя и повторном деплое SQLite сбрасывается: типы встреч и записи пропадают. Бесплатный сервис засыпает после 15 минут без запросов, первый запрос после этого занимает около минуты. Для постоянного хранения нужен платный тариф с диском, смонтированным в `/data`.

### Подключение Render MCP

Файл `.mcp.json` описывает сервер `render` (`https://mcp.render.com/mcp`). Секретов в репозитории нет: ключ берётся из переменной окружения.

1. Создайте ключ в Render: Account Settings → API Keys.
2. Задайте его в окружении, из которого запускается Claude Code: `export RENDER_API_KEY=...`. Не добавляйте ключ в Git; если он нужен в настройках проекта, положите его в `.claude/settings.local.json` и исключите файл из Git.
3. Запустите Claude Code в корне проекта и одобрите сервер `render` из `.mcp.json`.
4. Проверьте подключение: попросите показать список сервисов Render.

## Использование

С главной страницы владелец открывает «Админка», создаёт тип встречи и получает прямую ссылку. Гость открывает эту ссылку или переходит в каталог через «Записаться».

```bash
pnpm --dir backend dev
```

В другом терминале запустите фронтенд и откройте адрес, показанный Vite (обычно http://localhost:5173):

```bash
pnpm --dir frontend dev
```

Vite перенаправляет `/health` и `/api` на `127.0.0.1:3000`. Проверка API из терминала:

```bash
curl --fail http://127.0.0.1:3000/health
# {"status":"ok"}
```

Сборка и запуск собранного приложения:

```bash
pnpm --dir backend build
pnpm --dir backend start
```

`dev` и `build` сначала генерируют OpenAPI и сервер из TypeSpec. После изменения контракта перезапустите `dev` или выполните генерацию в другом терминале:

```bash
pnpm --dir backend generate
pnpm --dir backend typecheck
```

Переменные окружения: `HOST` (по умолчанию `127.0.0.1`), `PORT` (по умолчанию `3000`) и `DATABASE_PATH` (по умолчанию `call-calendar.sqlite` в рабочем каталоге бекенда). `FRONTEND_DIST` задаёт путь к каталогу собранного фронтенда для раздачи через бекенд. В Docker этот путь уже настроен.

Сборка фронтенда и отдельная генерация SDK (для обеих команд нужны установленные зависимости бекенда):

```bash
pnpm --dir frontend build
pnpm --dir frontend generate
```

Генерация сначала обновляет OpenAPI из TypeSpec, затем Orval создаёт клиент в `frontend/src/generated/`. Сгенерированные файлы не редактируются вручную. Dev-прокси предназначен для локальной разработки; для опубликованной сборки направьте `/health` и `/api` к бекенду и отдавайте `index.html` для страниц фронтенда.

[Устройство бекенда и правила генерации](backend/README.md).

## Релизы

Release Please отслеживает Conventional Commits в `main` и создаёт или обновляет PR с версией и `CHANGELOG.md`. После слияния этого PR он создаёт тег и GitHub Release. Версия относится ко всему приложению и хранится в `version.txt`; `0.0.0` — начальная точка, а не опубликованный релиз. Первый журнал изменений учитывает доступную историю коммитов. Docker-образ в реестр не публикуется; развёртывание на Render описано в разделе «Публичный деплой».

В настройках репозитория **Settings → Actions → General → Workflow permissions** необходимо разрешить GitHub Actions создавать pull request. Workflow использует встроенный `GITHUB_TOKEN`: созданный им release PR не запускает остальные workflow автоматически, поэтому перед слиянием выполните `mise run check` на его ветке. Если требуются автоматические проверки release PR или workflow по событию релиза, настройте отдельный GitHub App token или PAT и передайте его в action; права токена и правила защиты ветки определяются настройками репозитория.
